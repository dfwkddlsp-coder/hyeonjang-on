범용 서비스의 **1번 현장**이 된다. 큰 변경은 **시험용 사이트**(같은 코드, 별도 Worker·D1·R2)에서 먼저 써 보고 올린다.

## 0. 먼저 정리할 것 (코드 밖)
- **소유권**: 회사 업무로 만든 프로그램은 회사가 저작자가 될 수 있다(저작권법 제9조).
  판매·외부 제공 전에 근로계약·취업규칙의 지식재산 조항을 확인하고, 필요하면 회사와 서면으로 정리한다.
  이 현장의 실제 데이터(명단·전화번호·사진)는 범용판에 절대 가져가지 않는다.
- **개인정보**: 취약근로자 건강정보(혈압·검진)는 민감정보다. 불특정 다수에게 서비스하려면
  개인정보처리방침, 민감정보 별도 동의, 위탁(Cloudflare) 고지, 보관기간·파기 절차가 필요하다.

## 2. 범용판 구조 결정 (추천과 이유)
**여러 현장을 한 서비스에서 받는 방식(멀티테넌트)** 중 셋을 비교했다.

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 고객마다 배포를 따로 (Worker·D1·R2 한 벌씩) | 지금 코드 그대로, 데이터가 완전히 분리 | 고객이 늘면 배포·업데이트·백업이 고객 수만큼 늘어남 |
| **B. 한 배포 + 모든 표에 `tenant_id`** | 운영이 하나, 가입하면 바로 사용 | 모든 쿼리에 현장 구분이 빠지면 데이터가 섞임 → 막는 장치 필수 |
| C. 현장마다 Durable Object(SQLite) | 분리가 강하고 한 배포 | 구조를 많이 바꿔야 하고 백업·조회가 복잡 |

**추천: B.** 단, 데이터 접근을 `worker/lib/db.js` 한 곳으로 모으고(모든 SQL이 여기서 `tenant_id`를 붙임),
"다른 현장 데이터는 절대 안 보인다"를 API 테스트로 강제한다. 첫 고객 몇 곳은 A로 시작해도 된다(지금 코드로 바로 가능).

## 3. 단계별 계획
각 단계는 끝날 때마다 `npm run check` + `npm test` 통과, 로컬에서만 시험.

**0단계: 시험용 사이트 (먼저 할 것)**
- `wrangler.toml`에 `[env.staging]`: Worker `hyeonjang-on-staging`, 새 D1 `hyeonjang-on-staging-db`, 새 R2 `hyeonjang-on-staging-photos`
  (실제 현장 DB·R2를 절대 가리키지 않게). 배포 `npx.cmd wrangler deploy --env staging`
- 스키마 적용, 시험용 운영자 계정, 가짜 데이터(근로자·장비 몇 건). 실제 현장 데이터는 넣지 않는다
- 원격 D1·R2 생성은 운영자가 직접 실행(작은 .cmd 준비 + 무엇을 하는지 설명). CLAUDE.md 규칙 그대로
- 큰 변경의 순서: 로컬 `npm run dev` → 시험용 사이트 → 실제 현장 백업 → 실제 배포

**1단계: 코드 위생 (동작 변경 없음)**
- 화면 코드를 ES 모듈로: esbuild로 하나로 묶기 → `index.html` 순서 의존·전역 이름 충돌이 사라짐
- 포매터(prettier)로 한 줄 함수 풀기, `app.css`를 화면별로 나누기
- GitHub Actions: push마다 check + 로컬 wrangler로 API 테스트

**2단계: 테넌트(현장) 분리**
- `tenants` 표(이름, 상태, 요금제, 만든 날), `users`·`sessions`·`docs`·`blobs`·`login_fail`에 `tenant_id`
- 로그인 아이디는 현장 안에서만 유일(`UNIQUE(tenant_id, login_id)`). 휴대폰 번호 아이디가 현장끼리 겹칠 수 있음
- 현장 찾기: 주소(`<현장코드>.도메인`) 또는 로그인 화면의 현장 코드. 세션에 tenant_id 저장
- R2 경로를 `t/<tenant>/...`로. 백업·동기화·푸시 알림·초대 QR·가입 신청 모두 현장 단위로
- **격리 테스트**: 현장 A 사용자가 B의 문서·사진·사용자·백업을 어떤 API로도 못 보는지

**3단계: 가입과 첫 설정**
- "새 현장 만들기": 현장 + 운영자 계정 생성(이메일 인증 또는 승인제)
- 업종 템플릿: 지금 `DEF`·`EQF_DEF`(장비 양식, 점검 항목, 카테고리)를 "건설 현장 기본" 템플릿으로
- 첫 화면 안내(근로자 대장 엑셀 올리기 → 장비 대장 → 초대 QR)

**4단계: 서비스 운영**
- 요금제·한도(사용자 수, 사진 용량, AI 질문 수)와 결제
- 현장별 백업·내보내기·탈퇴 시 파기, 감사 기록(누가 무엇을 지웠나)
- 보안: 운영자 2단계 인증, 위험 작업 재확인, 로그인 기록(Claude 메모리의 `security-plan-operator-account`)
- 장애 알림, 오류 기록(지금의 `rejectlog`를 확장), 이용약관·개인정보처리방침

**5단계: 브랜딩**
- 서비스 이름·로고·도메인(현재 "현장ON"은 이 현장용 이름), 현장별 로고는 설정으로

## 4. 범용화할 때 다시 볼 "이 현장 전제"
